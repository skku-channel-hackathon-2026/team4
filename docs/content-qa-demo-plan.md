# D 전용 작업 설계서 — 콘텐츠·제품 검증·PR 검토·시연

- 담당: 김근형(D). A=화면, B=백엔드·공통 계약·통합, C=대화·검색.
- 작성일: 2026-09-19. 기준: 원격 main `fd6dd964b933ed3c5ed73fcb142746cab9601a35`.
- 목적: 다른 팀원의 개발을 기다리지 않고 사례와 평가 기준을 준비하고, 통합 후 같은 자료로 제품과 발표를 검증한다.
- 이 문서는 작업 계획이다. 아래 목표 수량·테스트·리허설은 완료 실적이 아니다.

## 1. D가 책임질 결과

“같은 학생 상황에서 행동을 바꾸면 어떤 선배 경험과 연결되며, 그 경험을 어디까지 믿어도 되는가”를 콘텐츠와 검증으로 설명한다. 최종 산출물은 검수한 사례 묶음, 재현 가능한 제품 검증 기록, PR별 제품 판단, 60~90초 음성 시연 영상과 백업이다.

최우선 순서는 팀플 대표 시나리오 완성 → 정정·사례 부족·오류 검증 → 실제 Desk 확인 → 녹화·음성 제작이다. 성적·동아리 콘텐츠 확충은 핵심 시연이 안정된 뒤 진행한다.

## 3. 병렬 작업과 인계 경계

| D의 독립 작업                            | 동시에 진행할 개발               | 개발자에게 넘길 것                           | 인계 완료 기준                                |
| ---------------------------------------- | -------------------------------- | -------------------------------------------- | --------------------------------------------- |
| 팀플 3개 행동의 사례·도구 검수           | A 비교 카드, B 사례 조회, C 검색 | 사례 ID, 행동, 관찰 결과, 비용, 적용 조건    | B/C가 동일 사례 ID로 로딩·검색 결과 확인      |
| 정정·거부·모름 등의 입력 대본 작성       | C 모델 추출·추가 질문 개선       | 입력 순서, 보존할 사실, 금지 응답, 판정 기준 | C 테스트 또는 수동 실행 기록과 연결           |
| 결과 문구와 가상 표시 검수 기준 작성     | A 화면·오류 상태 구현            | 표시 위치, 필수 문구, 화면별 합격 조건       | A가 화면 증거와 함께 확인                     |
| 사례 없음·중복 전송·재시도 시나리오 작성 | B 세션·저장·오류 처리            | 최소 재현 절차, 기대 화면 및 저장 결과       | B 기술 검증 + D 제품 재검증                   |
| 발표 구성·학생 대사·촬영 순서 준비       | A/B/C 통합 수정                  | 고정 입력, 핵심 장면, 제한 시간              | 통합 버전에서 실제 응답을 확보한 뒤 대본 확정 |

D의 기본 소유 범위는 이 문서와 콘텐츠·검증 기록이다. `packages/shared/src/cases.ts`의 사례 값은 D가 수정할 수 있지만, 시작 전 B에게 파일 점유를 공유한다. 공유 타입, 행동 태그 목록, 마이그레이션 순번, 모델·검색 로직은 B/C 소유다. 스모크 스크립트는 B와 수정 범위를 합의한 뒤에만 변경한다.

다른 팀원의 파일 수정이 진행 중이면 D는 아래 사례 템플릿으로 콘텐츠를 먼저 정리한다. 타입이나 DB를 별도로 설계해 병렬 구현하지 않는다. 인계 요청·회의·GitHub 댓글 게시 등 실제 공유는 별도 실행 작업이며, 이 문서 작성으로 수행한 것으로 간주하지 않는다.

## 5. 콘텐츠 제작·검수 규격

### 5.1 당장 사용할 팀플 기준 사례

| 현재 사례 ID            | 대응 행동               | 검수 초점                                                                    |
| ----------------------- | ----------------------- | ---------------------------------------------------------------------------- |
| `team-solo-night`       | `solo_completion`       | 제출 여부와 체력·연습 손실을 동시에 보여주는가                               |
| `team-inform-professor` | `inform_professor`      | 교수에게 전달한 사실과 이후 재분배를 분리하는가. 성적 보호를 보장하지 않는가 |
| `team-reduce-scope`     | `reduce_scope_reassign` | 범위를 줄일 수 있는 과제인지, 팀 합의가 가능한지 조건을 보여주는가           |

셋 모두 가상 사례다. 하나의 사례에 여러 행동이 들어 있으면 결과를 특정 행동 하나의 인과 효과로 표현하지 않는다. 검색에서 같은 사례가 여러 카드에 나오면 ID가 같다는 사실을 드러내고 독립된 선배 세 명으로 설명하지 않는다.

### 5.2 사례 작성 템플릿

현재 공통 `CaseSchema`를 유지한다. 콘텐츠 초안은 아래 항목으로 작성하고 B의 로딩·검증 경로를 거친다.

| 항목                               | 작성 내용·검수 조건                                                                        |
| ---------------------------------- | ------------------------------------------------------------------------------------------ |
| ID·버전·출처                       | 기존 ID 유지, 수정 시 버전 정책 B 확인. 실제/가상 명시                                     |
| category·title·problemType         | 기존 카테고리·문제 유형 사용. 제목은 행동과 경험을 구체적으로 표현                         |
| situation·constraints·urgency·goal | 상황 문자열, 제약 배열, `today/week/later/unknown`, 원했던 결과. 없는 사실은 보충하지 않음 |
| actionSteps                        | 순서, 기존 actionTag, 실제 수행한 행동 설명. 고민만 한 행동과 구분                         |
| outcome                            | shortTerm, followUp, unresolved. 관찰 결과와 미해결 내용을 분리                            |
| receipt                            | firstAction, wasted, turningPoint, cost, status. 시간·포기한 것·부담을 구체화              |
| conditions·tags                    | 적용 조건과 검색 키워드. 규정이 다른 학교·수업에도 일반화하지 않음                         |
| tool                               | title, body, usageNote. 현재 계약은 단일 도구이며 배열로 확장하지 않음                     |

`sourceType`, `status`, `createdAt` 등 저장 필드의 확정 방식은 등록 경로를 따르며, D가 임의로 승인된 실제 사례로 전환하지 않는다. 현재 선배 입력 경로의 실제/가상 처리 방식은 B와 확인한다. 가상 데이터를 실제 경험 제출 폼에 넣어 실제 사례로 보이게 만들지 않는다.

실제 경험을 수집할 때는 상황 → 행동 순서 → 이후 결과 → 비용 → 다음 사람에게 필요한 조건을 묻는다. 공개 사용 동의와 원본은 비공개로 관리하고 공개 저장소에는 익명화된 승인 내용만 넣는다. 확보가 안 된 경험을 실제 선배 사례로 꾸미지 않는다.

### 5.3 콘텐츠 합격 기준

- 표시된 결과·비용은 사례 원문에서 찾을 수 있다.
- 행동을 실제로 한 근거와 적용 조건이 있다.
- “이 행동을 하면 반드시 해결된다” 또는 성공 확률로 표현하지 않는다.
- 가상 사례 표시는 목록·비교 카드·상세에서 이해 가능하다.
- 도구에는 실행할 순서와 채울 빈칸이 있으며 개인정보·미확인 학사 규정을 포함하지 않는다.
- 문장이 자연스러운 것과 검색·등록 가능한 것은 별도 검사한다. 최종 콘텐츠는 공통 스키마 검증을 통과해야 한다.

Q01의 사례 후보는 위 팀플 3개를 사용하되 순위가 무조건 각각 다르다고 요구하지 않는다. C와 행동별 허용 사례 ID, 필수 행동 일치, 참고 사례 여부를 고정한다. 성적·동아리는 콘텐츠 인계 후 카테고리별 대표 입력을 추가한다. 다른 사용자 세션 접근·비승인 사례 차단은 B의 자동 테스트 증거를 D가 확인하며, 실제 타인의 데이터로 시험하지 않는다.

실제 모델 검증은 C가 실행하거나 비용·키·실행 환경을 합의한 뒤 수행한다. Q01~Q06은 최종 후보에서 각각 3회 실행을 목표로 하고 실패 횟수도 기록한다. 소수 회차의 통과율을 서비스 정확도·안전성 수치로 발표하지 않는다. 실제 화면 의미 검수는 자동 테스트 통과와 별도로 남긴다.

## 7. PR 검토 운영

각 검토 시작 시 원격 main과 해당 PR 최신 커밋을 갱신한다. 기준 SHA를 기록하고, main 이후 변경과 병합 시 충돌을 확인한다. 이전 리뷰 지적을 최신 코드에 그대로 재사용하지 않고 수정 여부를 다시 검증한다.

| PR 종류     | D가 볼 것                                                   | 기술 담당자에게 요구할 증거                                   |
| ----------- | ----------------------------------------------------------- | ------------------------------------------------------------- |
| A 화면      | 입력부터 도구 복사까지 동선, 가상 표시, 로딩·오류·사례 없음 | 변경 화면, 좁은 폭 캡처, 실제 API 연결 여부                   |
| B 서버      | 사용자 상황 보존, 재시도·확인·수정 흐름, 사례 출처          | 계약 변경 목록, 세션·권한 테스트, 저장·마이그레이션·배포 순서 |
| C 대화·검색 | 사실·해석 분리, 정정·거부, 행동 일치, 근거 없는 결과 여부   | 해당 Q 시나리오 입력/출력, 모의/실제 API 구분, 실패 기록      |
| D 콘텐츠    | 사례 원문·도구·기대 결과 일치                               | B/C의 스키마·검색 검증, 다른 팀원의 제품 검토                 |

리뷰에는 재현 가능한 문제, 사용자 영향, 수정 조건을 남긴다. 승인 여부는 PR 코드와 증거로 판단한다. D는 제품 수용 여부를, 코드 소유자는 기술 타당성을, B는 통합·배포 준비를 확인한다. D 리뷰 완료는 자동 머지 지시가 아니다.

새 main이 병합되면 영향을 받는 Q 항목을 다시 실행한다. 모델·프롬프트·사례·화면 응답이 바뀌면 발표 대본과 녹화본의 갱신 필요성도 확인한다.

## 8. 발표용 음성·영상 설계

음성은 발표 자료로 제작한다. 앱에 STT/TTS 기능을 추가하는 작업은 포함하지 않는다. 발표 초반에 “실제 앱 실행 화면에 발표용 음성을 입혔고, 사례는 가상 시연 데이터입니다”라고 설명한다.

### 8.1 80초 목표 장면 구성

| 시간    | 화면·행동                          | 음성·전달할 내용                                                             |
| ------- | ---------------------------------- | ---------------------------------------------------------------------------- |
| 0~8초   | 서비스 소개·카테고리               | “정답을 예측하는 대신, 같은 상황에서 다른 행동을 한 선배 경험을 비교합니다.” |
| 8~23초  | Q01 학생 입력                      | 학생 화자로 화면의 입력 원문을 읽음                                          |
| 23~40초 | 실제 추가 질문·학생 답변·상황 확인 | 서비스 화자는 실제 표시 응답을 읽음. 필요한 한두 턴만 선택                   |
| 40~62초 | 행동별 비교 카드                   | 내레이션으로 관찰 결과·비용 차이를 설명. 사용자 미래의 결과로 표현하지 않음  |
| 62~74초 | 사례 상세·도구 복사                | 적용 조건과 바로 사용할 도구 제시                                            |
| 74~80초 | 마무리 화면                        | “무엇이 정답인지보다, 선택의 비용과 조건을 보고 다음 행동을 정합니다.”       |

위 서비스 대사는 생성될 응답을 미리 작성한 것이 아니다. 최종 실행에서 나온 질문·요약을 전사해 확정한다. 서비스 음성은 화면 원문과 일치시키고, 카드 핵심을 줄여 설명하는 부분은 발표자 내레이션으로 구분한다. 자연스러운 입력 하나에 고정된 음성을 맞추려고 라이브 결과를 바꾸지 않는다.

### 8.2 제작 순서와 백업

1. B와 최종 후보 SHA·배포·provider·사례 버전을 고정한다.
2. 실제 team4 Desk에서 Q01을 완주하고 화면과 응답을 저장한다.
3. 사용자/서비스/발표자 대사를 구분해 전사하고 사실·가상 표시를 검수한다.
4. 본인·동의한 팀원의 녹음 또는 팀이 이용 가능한 음성 도구로 두 화자를 제작한다. 도구 선택·음성 생성은 별도 작업이다.
5. 실제 화면 녹화에 음성을 맞추고 자막을 넣는다. 대기 구간을 줄였다면 편집된 녹화 시연임을 밝힌다.
6. 발표 기기에서 소리·한글 자막·전체화면·오프라인 재생을 확인한다.

| 현장 상태          | 전환 방식                                           |
| ------------------ | --------------------------------------------------- |
| 정상               | 검증된 녹화 영상 재생, 추가 질의는 실제 앱으로 확인 |
| 네트워크·모델 오류 | 로컬 저장 영상으로 시연하고 녹화 시점·환경을 밝힘   |
| 음향 오류          | 같은 영상의 자막·무음 버전 + 발표자 직접 설명       |
| 영상 재생 오류     | 입력·상황 확인·비교·도구의 정적 캡처 4장 + 대본     |

발표에서 “음성 대화 기능 완성”, “일반 학생 누구나 접속 가능”, “검증된 성공 확률”을 주장하지 않는다. 현재 Desk 접근 범위와 가상 사례를 사실대로 설명한다.

## 9. 파일·브랜치 관리

- 이 문서는 `docs/content-qa-demo-plan.md` 하나로 작업 기준을 관리한다. 작성 브랜치는 `docs/content-qa-demo-plan`이며 최신 main에서 분기했다.
- 시나리오 실행·오류·대본·증거 링크는 이 문서에 필요한 내용만 덧붙인다. 별도 진행 문서를 만들지 않는다.
- 사례는 현재 원본 `packages/shared/src/cases.ts` 또는 B가 확정한 단일 등록 경로를 사용한다. PR #1 원본을 별도로 복제해 두 번째 기준 데이터를 만들지 않는다.
- 음성·영상 원본과 실제 경험 원문은 Git 밖 지정 폴더에 보관한다. 저장소에는 필요한 익명 캡처와 산출물 위치·버전만 기록한다.
- 모든 수정은 작업 브랜치에서 진행한다. 검토용 임시 작업 공간은 검증 후 정리하고, 기존 미커밋 설계서는 보존한다.
- 푸시·PR 게시·배포·운영진 연락은 준비된 결과를 바탕으로 각각 수행하고 실제 완료 여부를 기록한다.

## 10. 발표 준비 완료 판정

- 대표 팀플 흐름이 최종 배포에서 카테고리부터 도구 복사까지 통과했다.
- 카드의 행동·사례 ID·관찰 결과·비용을 원문과 대조했다.
- 정정·거부·목표 변경·모델 실패에 대한 결과와 남은 제한을 기록했다.
- 발표를 막는 이슈가 없고, 미해결 사항에는 담당자와 공개할 제한이 있다.
- A/B/C 변경을 최신 main 기준으로 검토했고, 최종 녹화가 해당 후보와 일치한다.
