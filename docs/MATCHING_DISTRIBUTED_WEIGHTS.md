# 분산 가중치 매칭 개선 · 2026-09-19

## 범위

`/tmp/team4-context-publish`, `kyu_beom-senior-matching`의 로컬 변경이다. 기준 main은 `d316e37`이며 별도 작업에서 병합된 PR #18을 이 dirty checkout에 다시 합치지 않았다. 기존 main UI를 유지하며 이번 개선은 H 이후 매칭 로직과 검증에 집중했다. 커밋·푸시·원격 배포 및 Gemini 호출은 하지 않았다.

## 발견한 편중과 수정

1. 실제 행동은 이미 필수 검색 조건인데 30점을 다시 부여했다. 점수에서 제거하고 필터로 유지했다.
2. 범주 일치 1.0과 낮은 문자열 유사도를 그대로 합치면 동일 배점에서도 문제 유형·시간이 지배했다. 문제 유형/상황/제약/목표/긴급도 **각 최대 20점**의 항목별 순위 합산으로 변경했다.
3. 시간 차이가 하나라도 있으면 무조건 후순위로 밀려, 내용이 전혀 다른 사례가 선택됐다. 합산 점수로 정렬하되 알려진 조건 차이는 reference 표시와 차이 설명으로 남긴다.
4. 같은 사실을 여러 필드에 복사하면 중복 점수를 받았다. 정규화한 토큰 집합이 동일한 텍스트 필드는 예산을 공유한다. 의미만 같은 바꿔쓰기는 아직 중복 판별하지 못한다.
5. 단순 부정문도 단어가 비슷하다고 높은 점수를 받았다. 거의 동일한 주제의 명시적 반대 서술을 해당 항목의 음수 기여와 조건 차이로 기록한다. 질문·이중 부정·인식하지 못한 부정은 확정하지 않는다.
6. 완결 문장 반복이 이중 부정처럼 처리되는 결함도 발견했다. 동일한 전체 메시지 반복을 먼저 접고 회귀 테스트를 추가했다.

## 점수 계산 계약

- 같은 카테고리, approved, 출처 모드, 실제 수행 행동은 필터이며 보너스 점수가 아니다.
- 후보별 원시 근거 점수를 계산하고 항목마다 양수 값의 서로 다른 순위를 구한다. `rankVote = 오름차순 순번 / 양수 고유 값 개수`.
- 양수 기여는 `배점 × rankVote × min(1, 원시값/근거문턱)`이다. 아주 약한 문장이 후보 중 최고라는 이유만으로 20점이 되지 않는다.
- 근거문턱은 기존 관련성 기준인 상황 0.12, 제약 0.22, 목표 0.25를 사용한다. 문제 유형·긴급도는 1. 아직 경험적 휴리스틱이다.
- 음수 근거는 해당 항목에서 최대 -20점. 모든 항목을 합친 이론적 범위는 -100~100이며 확률이 아니다. 단독 `scoreCase` 결과와 다른 후보 집합의 점수를 절대 척도로 비교하면 안 된다.
- 모르는 항목은 0점이며 다른 항목에 예산을 양도하지 않는다. 동일 텍스트가 여러 항목에 반복되면 학생/선배 쪽 중 더 큰 중복 개수로 배점을 나눈다.
- 긍정 근거가 한 항목 이하이면 강한 상황 일치(context≥0.5)를 제외하고 reference로 제한한다. 알려진 충돌은 점수와 별개로 reference다. 필수 적용 조건 충족을 보증하지 않는다.
- 내부 결과 `distributed`에 항목별 기여·예산·긍정 근거 목록을 남긴다. 실제 사용 화면에는 점수를 노출하지 않는다.

## 반복 실험 결과

모두 합성 사례다. 수정 전에 질문/정답을 고정했고 보고서 해시로 변경을 검사했다. 실제 사용자 일반화 정확도나 모델 학습 성과가 아니다.

| 실험                       | 변경 전 |    최종 |
| -------------------------- | ------: | ------: |
| 기존 고정 평가             |   22/22 |   22/22 |
| 편중 대조 개발 질문        |     0/9 |     9/9 |
| 편중 대조 분리 검증 질문   |     6/9 |     9/9 |
| 어려운 표현 진단           |     3/6 |     5/6 |
| 최종 46개 질문의 변형 검사 |       — | 184/184 |

중간 단계에서 단순히 배점만 20씩 나누면 개발 질문 3/9만 통과했다. 항목별 순위와 근거 강도를 함께 사용한 뒤 9/9가 됐다. 이 선택 후 분리 검증 9개를 열어 확인했다. 이후 재실행에는 이미 본 세트를 사용했으므로 최종 결과는 완전한 외부 독립 검증이 아니다. 진단 세트 또한 부정문 결함 수정에 사용했으므로 회귀 세트다.

변형 검사는 저장 순서, 결과·비용 문구, 숨김 상태, 반복 입력의 4가지이며 추가 독립 질문으로 세지 않는다. 벤치마크 정답 ID는 변경하지 않았다. 기존 golden 테스트의 상태 검사는 새 대표가 알려진 시간 차이를 가지면 reference를 기대하도록 출력 계약에 맞췄다. 이를 정확도 향상으로 세지 않는다.

문제 유형·상황·목표의 기여를 확인했다. 제약·시간을 빼도 이 세트에서는 결과가 같았다. 이 결과만으로 두 항목이 쓸모없다거나 모든 데이터에서 균등하게 기여한다고 주장할 수 없다. 제약/시간이 결정적인 별도 실제 사례를 추가해야 한다. 구현상 최대 배점의 분산과 실제 데이터에서의 기여 균등은 다른 문제다.

## 남은 실패와 다음 검증

`challenge-paraphrase`: “조원이 읽씹 중이에요”를 “팀원과 연락이 닿지 않는다”에 충분히 연결하지 못한다. 잘못 고른 후보는 reference로 낮췄지만 **순위 오류는 남아 있다**. 문장별 동의어 예외를 늘려 이 테스트만 통과시키지 않았다. 단순 부정 검사도 범용 의미 이해가 아니며 복잡한 부정 범위·시점·조건문은 한계가 있다.

다음 단계는 팀원이 새 카테고리별 실제 표현에 관련/무관/핵심 조건 차이 정답을 붙인 비공개 평가를 만드는 것이다. 그 뒤 main의 모델이 추출한 검증 가능한 의미 필드나 소수 후보 의미 재평가를 별도 실험한다. 이번 수치만으로 임베딩/LLM 도입 효과를 가정하지 않는다. 기존 단어 기반 비교는 빠른 기본선으로 유지한다.

## 코드와 재실행

최종 검증: 서버 테스트 110개, 전체 타입 검사, lint, 포맷 검사, Cloudflare 빌드가 통과했다. 반복 입력 결함 수정 후 일반 22개와 편중 대조 18개도 다시 실행해 유지됨을 확인했다(`verified-standard`, `verified-distributed`). 이번에는 UI를 새로 변경하거나 실제 채널/Gemini 연결을 시험하지 않았다.

- `server/src/failfair/distributed-score.ts`: 분산 합산/중복 예산/항목 제외.
- `server/src/failfair/retrieval.service.ts`: 필터/각 항목 근거/조건 차이/결과 상태.
- `server/src/failfair/polarity-comparison.ts`: 보수적인 단순 반대 서술 검사.
- `server/src/failfair/evaluation/fixtures/distributed-matching.ts`: 3개 카테고리 × 6개 대조 질문.
- `server/src/failfair/evaluation/matching-benchmark.ts`: 고정 세트 비교와 항목 제외 실험.

서버 디렉터리에서 실행:

```sh
node --import tsx --test src/*.test.ts src/failfair/*.test.ts
node --import tsx src/failfair/evaluation/matching-benchmark.ts --label next-standard
node --import tsx src/failfair/evaluation/matching-benchmark.ts --suite distributed --label next-distributed
node --import tsx src/failfair/evaluation/matching-benchmark.ts --suite challenge --label next-challenge
node --import tsx src/failfair/evaluation/matching-benchmark.ts --suite distributed --omit context --label next-without-context
```

이번 보고서는 Git 제외 디렉터리 `server/evaluation-results/`의 `balanced-standard`, `balanced-dev`, `balanced-validation`, `balanced-challenge-fixed`, `ablation-*` JSON에 있다. 각 파일명 앞에는 `matching-benchmark-`가 붙는다. `--baseline evaluation-results/이전파일.json`으로 같은 질문의 개선/퇴행을 비교한다. 기존 label은 덮어쓰므로 새 이름을 사용한다. 진단의 알려진 미해결 실패는 기록하되, 퇴행·변형 불변성 실패는 종료 코드 1로 처리한다.
