# 대화 분류 일반화 점검 및 수정

## 결론

사용자의 우려는 타당하다. 고정 JSON은 전달 계약이므로 유지해도 된다. 현재 작업은 모델 가중치 학습(fine-tuning)이 아니라 프롬프트·후처리 조정이다. 통계적 과적합을 증명한 것은 아니지만, 적은 시나리오 반복과 문장별 규칙에 의존하여 새로운 표현에서 실패하는 문제가 재현됐다.

검토 기준: `kyu_beom`의 `e7885ed` 및 Claude 변경 `be2cb2d`, PR #11의 변경 설명. 기존 4개 시나리오 반복 성공은 새로운 표현의 분류 정확도를 보장하지 않는다.

## 검증

- 서버 자동 테스트 79개 통과. 새 기간 경계, 근거 누락, 의역 허용, 상태 보존, 일괄 교정 검증 포함.
- 타입 검사, 포맷 검사, Cloudflare 빌드 통과(마지막 스키마 설명 변경 전 빌드 포함).
- 실제 Gemini 3.1 Flash-Lite에 합성 대화 실행. 규칙 기반 대체 없이 GeminiGateway를 직접 검증.
- 첫 확장 평가: 7개 중 3개 통과. 누락 근거, 시간 정정, 부정한 조건의 제약 분류 오류 확인.
- 공통 기준·일괄 교정 수정 후 전체 재평가: 7개 중 6개 통과. 부정한 조건을 제약으로 저장하는 한 건은 여전히 실패하여 기록을 유지함.
- 마지막으로 응답 스키마에도 제약 정의를 명시한 뒤 실패 사례 `unseen-negation` 개별 재검증 통과. 결과 `gemini-1789804766658.json`. 최종 버전 전체 7개를 재실행한 결과는 아니며, 단일 성공으로 안정성을 보증하지 않음.
- 원본 결과는 로컬 `server/evaluation-results/gemini-1789804634108.json`, `gemini-1789804729192.json`. 합성 대화 및 모델 응답이 포함되며 Git에는 올리지 않음.

## 남은 한계와 다음 작업

1. JSON의 형식·원문 인용 검사는 의미 이해의 정확도와 다르다. 원문 인용이 있어도 잘못된 유형이나 제약으로 분류할 수 있다.
2. category는 사용자가 먼저 선택한 분류를 유지하는 구조다. 현재 구현은 임의의 모든 고민을 새 category로 자동 분류하는 서비스가 아니다. problemType은 목록에 확실히 맞을 때만 선택하고 불명확하면 생략하도록 되어 있다.
3. 운영 환경은 Gemini 실패 시 기존 RuleBasedGateway로 대체한다. 이 경로는 이번 실제 평가의 대상이 아니며 의미 이해 품질이 낮을 수 있다. 실패율과 대체 실행률을 별도로 측정해야 한다.
4. 이번에 확인하고 수정에 사용한 새 시나리오도 이제 개발용 회귀 세트다. 이를 독립 평가 데이터라고 부르면 안 된다. 팀원이 작성한 별도 대화(동일 숫자·다른 맥락, 부정, 정정, 구어체, 복수 문제, 긴 대화)를 확보하여 수정에 사용하지 않고 평가해야 한다.
5. 자동 평가의 일부는 키워드 기반 누락 검사다. 의미 정확도나 사용자 전체 성공률로 해석하면 안 된다. 제약의 부정·분류 적합성·정정 반영은 사람이 함께 검토해야 한다.
6. 상태를 지키기 위해 토글 off에서도 최소 contextMeta가 생길 수 있다. 외부 전달은 기존 toLegacySituation 투영을 유지한다.

권장 방향: JSON 키는 고정하고 상황·제약·목표 값은 자유롭게 표현한다. 예외 문장 목록을 늘리는 대신 필드 의미와 불확실성 처리를 명확히 하고, 새로운 독립 대화에서 평가한다.
