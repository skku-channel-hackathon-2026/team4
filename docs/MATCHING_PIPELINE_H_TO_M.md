# H → M: 행동별 사례 매칭과 복구 도구 연결

기준 main: `d316e37`. 브랜치: `kyu_beom-senior-matching`.
UI 컴포넌트·레이아웃과 결과 응답 키는 그대로 유지한다. PR #18의 새로운 학생 맥락 구조에 의존하지 않는다. 현재 main의 Situation과 승인된 Case 데이터로 실행된다.

## 파이프라인 구현

| 단계         | 처리                                                                                                                                                                                                                                           | 구현                                                             |

| J → K        | 수행 행동·유사 표현·시간 차이 등 설명 제공. 원문 조건은 그대로 제공하고 충족 여부는 확인 필요로 표시                                                                                                                                           | scoreCase, buildResult                                           |
| K → L        | 행동별 사례, 실제 기록된 결과·비용·조건 전달. 같은 사례가 여러 카드에 나오면 중복 근거임을 명시                                                                                                                                                | matchActions, 기존 Compare/ActionCard UI                         |

## 매칭 방식

개인 프로필 추천이 아니라 **비슷한 상황에서 해당 행동을 한 선배의 경험 사례**를 찾는다. 선배 데이터에 정형 GPA·수강 학점·학과 필드가 없으므로 이 값을 만들어내서 정밀 매칭하지 않는다.

1. 같은 카테고리의 승인된 사례만 후보로 사용한다. 미승인·숨김 데이터는 순위에서 제외한다.
2. 실제 actionSteps에 학생 행동 태그가 있으면 행동 일치 후보로 우선 배치한다.
3. 같은 행동 일치 그룹 안에서는 다음 점수를 사용한다.

| 요소      | 가중치 | 비교                                                                                   |
| --------- | -----: | -------------------------------------------------------------------------------------- |
| 문제 유형 |     30 | 동일 problemType                                                                       |
| 상황·진행 |     30 | 학생 situation/progress와 사례 situation/title/tags                                    |
| 제약      |     20 | 학생 제약별 최선의 사례 제약 유사도를 평균. 제약 하나의 단어 일치로 만점 처리하지 않음 |
| 목표      |     15 | goal 텍스트 유사도                                                                     |
| 남은 시간 |      5 | 알려진 urgency가 일치하는지                                                            |

텍스트 비교는 단어와 2~3글자 특징을 사용하는 이진 TF-IDF 코사인 유사도다. 조사 차이가 있어도 일부 관련 표현을 찾고 반복 단어로 점수가 올라가지 않는다. 숫자 토큰을 부분 분해하지 않아 `13일`이 `3일`로 매칭되지 않는다. 맥락 없는 숫자만으로 유사성을 만들지 않는다.

가중치는 초기 휴리스틱이며 실제 정답 데이터에서 학습·보정된 값이 아니다. 점수는 내부 정렬용 0~100이며 성공 확률이나 검증된 정확도가 아니다. Gemini/임베딩 API 호출·추가 키·외부 전송이 없다.

## matched / reference / no_case

- matched: 같은 카테고리에서 그 행동을 실제로 한 기록. 상황 유사도가 낮으면 “행동은 같지만 상황 정보는 부족함”을 표시한다. 적용 가능성이나 성공을 보증하지 않는다.
- reference: 해당 행동을 한 후보가 없을 때 관련 상황의 사례를 보여주되 그 행동은 하지 않았다고 명시한다.
- no_case: 행동 태그를 연결할 수 없거나, 행동 일치도 없고 최소한의 상황 관련성도 없는 경우.

상황 관련성 문턱은 동일 문제 유형 또는 context≥0.12 / constraints≥0.22 / goal≥0.25 중 하나다. 시간만 같다는 이유로 참고 사례를 만들지 않는다. 실제 같은 행동을 한 사례는 문턱 미달이어도 제한 안내와 함께 제공한다. 동점은 사례 ID순으로 고정한다.

## 근거와 조건

결과·비용·영수증·도구를 생성하지 않고 저장된 사례에서 읽는다. 성공/실패 결과는 순위 점수에 사용하지 않아 성공담만 우선하지 않는다. `sourceType`을 그대로 넘겨 가상 사례 배지를 유지한다.

자유문장 조건의 충족 여부를 자동 판정하지 않는다. 원문 조건을 카드/상세에 제공하고 학생의 확인이 필요하다고 표시한다. 같은 사례의 다중 행동을 독립된 경험 여러 개처럼 세지 않도록 기존 differences 영역에 안내한다.

## 검증 방법

```sh
pnpm --filter @tutorial/shared build
pnpm --filter @tutorial/server test
pnpm --filter @tutorial/server test:matching
```

마지막 명령은 서버의 `evaluation-results/matching-report.json`에 카테고리별 후보·요소 점수·최종 카드를 기록한다. 데이터는 번들 가상 사례이며 실제 학생 데이터나 모델 응답이 아니다.

통합 테스트는 H 이후 실제 함수와 세션/사례/피드백 SQL을 실행한다. D1 호환 SQLite 대역에서 중복 요청, 승인 사례 검색, 결과 재조회, 영수증/도구 원문, 피드백 저장, 접근 거부를 확인한다. 브라우저 클립보드와 실제 Channel Talk 배포를 자동 실행한 테스트는 아니다.

## 한계와 이후 확장

문자 기반 검색은 완전한 의미 이해가 아니다. 표현이 전혀 다른 동의어·부정문·복잡한 조건은 오판할 수 있다. 이를 보완하려면 독립된 정답 사례로 평가한 뒤 임베딩/재순위화 단계를 추가한다. 이번에는 특정 시연 대본이나 사례 ID를 예외 규칙으로 넣지 않았다.

새 구조 PR #18이 합쳐지면 검증된 사실/선호/제약을 검색 문서로 투영하는 어댑터를 추가할 수 있다. 미확인·추정을 확정 제약으로 사용하지 않아야 한다. 후보 데이터가 많아지면 현재 메모리 비교를 검색 인덱스로 옮길 수 있다.

## channel.works에서 실행하기

브랜치 push / PR 생성만으로 운영 앱은 바뀌지 않는다. 이 PR을 `main`에 병합하고 main CI가 성공하면 운영자의 배포 컨트롤러가 Cloudflare Workers 배포를 시작한다. CI 성공과 배포 완료는 별개이므로 반영되지 않으면 운영자에게 배포된 커밋을 확인한다.

1. [성균관대 해커톤 검증 그룹](https://channel.works/xd1l0/team-chat/groups/609235)을 연다.
2. 커맨드 목록에서 **SKKU 2026 Team4** 앱의 **망선박 / failfair**를 선택하고 학생 모드로 연다. 등록이 아직 이전 버전이면 `/tutorial`에서 같은 팀4 앱을 선택한다. 서버에는 이전 커맨드 호환 함수가 있다.
3. 카테고리 → 고민 입력 → 필요한 추가 질문 → 상황 확인 → 행동 선택·확인까지 진행한다. 이 PR의 검증 시작점은 확인된 행동을 비교하는 H 단계다.
4. 행동별 카드에서 선배가 실제로 한 행동, 관찰된 결과·비용, 차이·적용 조건을 확인한다. 참고 사례 / 사례 없음과 가상 사례 표기도 확인한다.
5. 사례 상세의 복구 영수증과 도구를 확인하고 복사·도움됨 피드백을 실행한다. 같은 사례가 여러 카드에 나오면 중복 근거 안내가 있어야 한다.
6. 배포 전부터 열린 화면은 닫고 새로 열어 테스트한다. 실패한 단계와 시각, 표시된 오류를 기록한다. 학생 고민·API 키는 공유 로그에 붙이지 않는다.

팀4 서버는 `https://skku-team4.skku-hackathon-2026.workers.dev`다. 서버 주소를 일반 브라우저에서 여는 것만으로 Desk 인증·WAM 연결까지 검증되지는 않는다. 테스트 데이터가 없으면 승인된 사례를 준비해야 하며, 가상 사례는 실제 선배 경험으로 소개하지 않는다.

이번 PR에는 새 DB 마이그레이션과 새 함수 이름이 없다. 기존 main의 D1 마이그레이션 적용과 앱 등록 상태는 운영자가 확인해야 한다. 매칭 자체는 추가 API 키가 필요 없지만 앞 단계의 Gemini 상황 추출에는 기존 서버 설정이 필요하다.

병합 전에 channel.works에서 시험하려면 별도 개발 앱과 HTTPS 개발 서버를 연결해야 한다. 공용 팀4 앱 주소를 개인 개발 서버로 바꾸지 말고 운영자와 별도 테스트 앱을 준비한다. 로컬 H→M 동작은 위 통합 테스트와 매칭 보고서로 먼저 확인할 수 있다.
